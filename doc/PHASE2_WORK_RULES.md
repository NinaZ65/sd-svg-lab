# Lab 2 工作规范

本文件执行 [项目规约](PHASE2_SPEC.md)；课程原文以 [Lab 2 要求](requests/lab2/phase_cli_2.md) 为准。设计改变时先更新规约或 ADR，并在 `doc/WORKLOG.md` 记录原因及验证证据。

1. **保留基线。** 不改写已有 Git 历史，不移动 `final`。先保存 `final` 的 CLI 会话输出作为无可选插件的兼容基线。原始课程材料放在 `doc/requests/`；本阶段截图放在 `doc/evidence/lab2/`，不得把要求中的示意图当作实际效果。
2. **按课程节点提交。** 依次完成 VSCode 实践、四扩展点与兼容回归、命令插件、box 的代码/配置两种装配证明、树标签、收尾报告。每个节点提交可运行的代码和相关测试，提交信息说明真实变化；`p2` 只打在全部验收后的最终提交上。
3. **遵守依赖方向。** 内核不得导入宿主或插件；插件不得导入宿主、其他插件或内核内部实现。代码装配只在一个顶层组合根追加插件。配置装配新增插件时不改已有运行源码；用实际提交的父子差异证明，而非只看最终目录。
4. **先定义契约再接入插件。** 扩展点须有名称、职责、调用点、缺省行为和失败报错。插件注册先暂存后校验，成功才发布；任何错误仅回滚当前插件。属性修改先验证并保留逆操作，成功后再记录一次历史。
5. **测试服务于风险。** 保持 `npm test` 通过，并增加独立插件测试、加载器全部失败分支、box 结构与读回、dirty 状态机、VSCode 层级/无 id/更新/不完整 XML。`dir` 同时用替身和真实临时目录验证。双装配会话逐字节比较，测试时目录内容固定且日志置于目录外。
6. **保留真实证据。** VSCode 文件标记和大纲定位截图必须由实际扩展运行取得；记录启动与安装步骤。指标脚本从 `final`、`p2` 的 Git 对象生成数字，不手填。正式报告在 `doc/README.md`，简短提交说明在 `doc/submissions/lab1-phase2/提交说明.md`，明确列出正式报告的具体路径。
7. **最终核验。** 检查构建、自动测试、CLI 会话、VSCode 手工演示、差异判据、文档链接、指标、Git 状态及远端引用。完成后推送普通提交与 `p2` tag，并分别核对本地和远端指向。
